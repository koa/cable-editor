# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Fiber-optic cable / duct / patch-panel planning tool. Single deployable binary: a Rust (actix-web) backend serving a GraphQL API plus an embedded Yew (WASM) SPA. Data lives in PostgreSQL + PostGIS; planned panel/port changes can be synced to NetBox. Domain names are partly German (`kabel` = cable, `schacht` = manhole/cabinet, `trasse` = duct route, `sequenz`); code comments and log messages are English, never mixed with German (older code still has German ones: translate the comments of the code you change), while the documentation in `docs/` and everything users see is German. Values built once and never changed are `Box<[T]>` / `Box<str>`, not `Vec` / `String`, unless a library needs those (diesel entities and inserts, GraphQL input types, cynic fragments, Yew and PatternFly props) or they only pass on what a library returned.

Concepts for work not yet done live in `docs/`, one file per topic: `docs/leitungskataster.md` (the quarterly INTERLIS delivery to the Leitungskataster Kanton Zürich, SIA405 LKMap; implemented up to the manual upload to the Checkservice: one delivery for the whole network, both transfer files as ZIPs and the log of deliveries in `backend/src/lkmap/`, the admin page `pages/lkmap.rs`), `docs/stammdaten.md` (pages for owners and Schacht types), `docs/navigation.md` (every page under the plan's path), `docs/netbox-sync.md` (syncing the circuits of the plan active in Netbox after every change and every few hours, the issues stored for admins; implemented), `docs/fehlermeldungen.md` (how errors reach the user; implemented), `docs/frontend-konventionen.md` (the same names, menus, links, error handling and confirmation of changes on every page; draft, being implemented step by step).

## Workspace layout

Cargo workspace (`default-members = cable-editor-binary`):

- `cable-editor-common` — shared by backend and frontend (serde only, builds for wasm): `UserError`, why a request was refused, and the limits/formats it checks (`limits`, e.g. `is_uid`).
- `cable-editor-backend` — library: Diesel models/migrations, async-graphql schemas, NetBox client, the delivery to the Leitungskataster (`lkmap/`: one delivery for the whole network: the SIA405 LKMap transfer file and the Zuständigkeitsperimeter, each in a ZIP, with a checksum telling whether the data changed since a delivery; `lkmapExport`, `downloadLkmap` logs the download in `lk_lieferung`, `setLkmapDelivered` confirms it).
- `cable-editor-binary` — actix-web server (`main.rs`): wires OIDC/JWT auth, DB pool, Prometheus, and embeds `cable-editor-frontend/dist` via `rust-embed` (SPA fallback to `index.html`).
- `cable-editor-frontend` — Yew + PatternFly + Leaflet SPA, built with Trunk for `wasm32-unknown-unknown`. Not built by plain `cargo build` from the root. Label printing uses the external `brady-web-sdk` crate (git dependency, `https://git.panter.ch/open-source/brady-web-sdk-rs.git`, pinned in `Cargo.lock`).
- `cable-editor-chart` — Helm chart; CI (`.github/workflows/build-and-publish.yml`) pushes the Docker image and chart to GHCR on pushes to `master` (snapshot versions, e.g. `sha-a1b2c3d`) and on `vX.Y.Z` tags (the real version). The workspace version (`Cargo.toml`'s `[workspace.package]`, every crate follows it with `version.workspace = true`) and the chart's `version`/`appVersion` are kept equal; `.github/workflows/release.yml`, started by hand with a `patch`/`minor`/`major` choice, bumps all of them together, commits, tags and pushes, then triggers `build-and-publish.yml` for that tag (a tag pushed with the workflow's own token doesn't trigger other workflows by itself, so that last step is explicit).

```sh

local/run-local.sh
local/import-data.sh              # load local/data.sql into the cable-db container
local/mock/run-mock.sh            # frontend on :8099 against a mock backend (no DB/Keycloak): fake OIDC login, in-memory GraphQL data
local/realdb/run-realdb.sh        # real backend on :8080 against a throwaway PostGIS from nix, login via the mock; checks: node local/realdb/check.mjs
local/lkmap/validate.sh <file.xtf>   # ilivalidator (downloaded once, Java from PATH or nix) against the SIA/canton model repositories
local/konventionen/run.sh         # frontend conventions (docs/frontend-konventionen.md): static rules, then every route in a browser against the mock, per role; run it before every review of a frontend change (SKIP_BUILD=1, VERBOSE=1)
node local/mock/screenshot.mjs [--desktop] [--full] /plan/0/cabinet/1/overview   # Playwright screenshots (phone by default), reports layout overflow and console errors

# Frontend (from cable-editor-frontend/; pre_build hook runs `npm install` in node/)
trunk serve                       # dev server on :8082, proxies /graphql and /graphql_anonymous to :8080
trunk build [--release]           # outputs dist/, which the binary embeds

# Backend server (root) — needs DATABASE_URL (from .env) and config.yaml
cargo run                         # API on :8080, /metrics, /health (liveness) and /ready (DB reachable) on :9080 (port + 1000)
cargo build -p cable-editor-frontend --target wasm32-unknown-unknown   # typecheck frontend
cargo clippy --workspace          # (frontend needs the wasm target to compile cleanly)
# The frontend build script links the backend, so libpq must be installed (-lpq) even for wasm checks.

# Release container
docker build .
```

Tests: only unit tests of plain logic so far, `cargo test -p cable-editor-backend` (e.g. fitting a duct's course, `graphql/duct_line.rs`). Against a real database without podman or Keycloak: `local/realdb/run-realdb.sh` (PostgreSQL 16 with PostGIS from nix, fresh on every start, the login of the mock backend, the backend applying the migrations, then `local/data.sql`; app on :8080, `REALDB_ROLE` for the role), then `node local/realdb/check.mjs` builds cables, panels, port usages and plans through GraphQL and checks the loaders (with `PG_LOG` also the number of SQL statements per query), the PostGIS conversions, fitting a duct's course, the changed ports of a plan, what a port holds in a plan (a fiber removed in it leads nowhere), the trace of a circuit from connector to connector, the refusals of mutations the delivery to the Leitungskataster (export, ZIPs, the log of deliveries) and the automatic Netbox sync (against the mock's Netbox without circuits, which counts its queries), the files validated with `local/lkmap/validate.sh` (`SKIP_ILIVALIDATOR=1` leaves that out).

**Build order matters:** the binary embeds `cable-editor-frontend/dist` at compile time, so run `trunk build` before building the binary (the Dockerfile does frontend first, then the musl backend build).

## Configuration

- `DATABASE_URL` env var (`.env`, loaded by dotenvy). Migrations in `cable-editor-backend/migrations` are embedded and run automatically at startup (`run_sync_migrations`).
- `config.yaml` (gitignored) with `oauth:` (`auth_client_id`, `auth_issuer`, optional `user_info_url` (default: `userinfo_endpoint` from the issuer's OIDC discovery), optional `auth_scopes` (space separated scopes the frontend requests, default `openid profile groups offline_access`; `offline_access` is what makes the provider issue a refresh token, e.g. Pocket ID only does so with it requested, without which the frontend's automatic renewal silently fails once the access token expires), `planner_groups` / `admin_groups` (space separated OIDC group names, see Authorization), `server_port`, optional `instance_name`, ...), `netbox:` (`url`, `token`, `provider_id`, `type_id`, optional `sync_interval_h`, how often the automatic sync runs at least, default 4) and the optional `lkmap:` (`datenlieferant_uid`, optional `datenherr_uid`, default the deliverer, `oid_prefix`, `perimeter_puffer_m`, the delivery to the Leitungskataster, validated at startup, see `docs/leitungskataster.md`) sections; each value can be overridden by env vars with prefix `APP` and `__` separator (see `backend/src/config.rs`).
- `LOG_LEVEL` env var controls `env_logger`.
- `oauth.instance_name` (env `APP__OAUTH__INSTANCE_NAME`, Helm `config.instanceName`) names an installation other than the productive one, e.g. `Dev`: `binary/src/instance.rs` then serves the manifest as "Cable Editor (Dev)" / "Cable Dev" in orange, the page title with the name and the icons of `assets/icons/dev/` (orange with "DEV", rendered from the SVGs by `local/mock/render-dev-icons.mjs`) in place of `assets/icons/*`, so the installed app is told apart on a phone (iOS and Android keep icon and name from install time: add the app anew).
- Helm chart (`cable-editor-chart`): `config.netboxSyncIntervalHours` sets `sync_interval_h`. The Netbox token comes from an existing Secret (`config.netboxTokenSecret.name`/`key`) or from `config.netboxToken`, which the chart stores in a Secret of its own; either way the Deployment only references it. Rendering fails without one.

## Architecture

### GraphQL: two schemas, typed end-to-end with cynic
- Backend exposes `/graphql` (authenticated: `graphql/authenticated/` — `Query`, `mutation/` with one object per kind of thing changed (`cable.rs`, `schacht.rs`, `duct.rs`, `panel.rs`, `plan.rs`, `owner.rs`, `schacht_typ.rs`, `lkmap.rs`) merged into `Mutation` (`MergedObject`), `planned.rs`) and `/graphql_anonymous` (`graphql/anonymous.rs`).
- `cable-editor-frontend/build.rs` depends on the backend crate, calls `create_authenticated_schema()` / `create_anonymous_schema()`, writes the SDL to `cable-editor-frontend/graphql/*.graphql` (gitignored), and registers them with `cynic_codegen`. Frontend queries are `cynic::QueryFragment` structs in `frontend/src/graphql/{authenticated,anonymous}/*.rs`, so **any backend schema change is checked at frontend compile time** — change the backend resolver, then fix the frontend fragments.
- `cable-editor-backend/build.rs` registers `schema/schema.graphql` (the NetBox GraphQL schema) for the cynic-based NetBox client in `src/netbox/`.

### Per-request transaction
In `binary/src/main.rs`, each authenticated GraphQL request: validates the JWT (`actix-4-jwt-auth`), fetches OIDC userinfo (cached 30s) into `UserInfo`, opens a pooled connection, runs `BEGIN`, and puts it into the request data as `Arc<tokio::Mutex<Object<AsyncPgConnection>>>`. Resolvers obtain it via `graphql::authenticated::get_connection(ctx)`. The whole request is `COMMIT`ed if there are no errors, otherwise `ROLLBACK`ed — so resolvers should return errors rather than manage transactions themselves: one transaction per atomic action, no nested `connection.transaction(...)` (it would only be a savepoint); functions doing database work take the connection and run on the caller's transaction. A background action is one transaction too (`netbox/auto_sync.rs`: one per run).

The schema references other objects as objects, never as bare ids (`Duct.schachtA: Schacht!`, not `schachtAId`). To keep that from costing a query per object, such references and the per-object lists of listed objects (a duct's Schächte, a Schacht's type and root panels, a cable's ducts (its path) and length, a cable end's port usages, which `FiberEnd.usedPort` picks from, a panel's ports (`PanelPorts`), what a port holds in a plan (`EffectiveUsage`), ports, panels, plans) go through `graphql/loader.rs`: an async-graphql `DataLoader` (created per request in `main.rs`) on the same shared connection, so it sees the transaction, and batches the keys of one request into one query per kind (`load_one(ctx, SchachtId(id))`). A resolver must not hold `get_connection`'s guard while awaiting the loader, that deadlocks — load its own rows first, drop the guard, then load the references (see `Schacht.connectingDuct`).

### Authorization
Tokens must carry the client id in `aud` (Pocket ID does so by default, the local Keycloak realm has an audience mapper). Every logged in user may read (restrict logins at the provider, e.g. Pocket ID's allowed user groups). `graphql/authorization.rs` maps the `groups` from the userinfo to a `Role` (`Reader` < `Planner` < `Admin`) via the config's `planner_groups` / `admin_groups` (group names, in Pocket ID not the friendly names). **Every mutation needs a `#[graphql(guard = "RoleGuard(Role::…)")]`**: Planner for plans and the master data (cables, panels, ports, Schächte, ducts), Admin for `implementPlan`, `setNetboxActivePlan`, `syncNetbox` (and the fields `issues`, `error` of the query `netboxSync`), deleting master data (`deleteCable`, `deleteSchacht`, `deleteDuct`) and changing owners (`createOwner`, `updateOwner`, `setDefaultOwner`, `deleteOwner`; the owner's name is the `Eigentuemer` of its objects in the delivery to the Leitungskataster) and Schacht types (`createSchachtTyp`, `updateSchachtTyp`, `deleteSchachtTyp`; the type gives the Objektart) and the delivery to the Leitungskataster (the query `lkmapExport` too, `downloadLkmap`, `setLkmapDelivered`). `currentUser.role` tells the frontend what to hide: `components/user.rs` `UserProvider` provides the `Role` as context (`util::get_role`), `AppRoute::required_role` names the pages needing more than `Reader` (the panel editors, a new Schacht, cable or duct, a new Schacht type, the Leitungskataster, Netbox), `RequireRole` guards them and `MenuDropdown` leaves them out; pages hide or disable their change buttons themselves (the cable page is read-only for readers). `UserMenu` at the end of the breadcrumb bar shows the user, the role and the provider's groups for support. The mock backend takes the role from `MOCK_ROLE` (`DENIED` refuses the login) and the result of the last Netbox sync from `MOCK_NETBOX` (`OK`, `ISSUES`, `FEHLER`, anything else: none yet) and the mutations failing like a broken database from `MOCK_FAIL` (comma separated names, `*`: all; `/mock/fail?mutations=…` changes it while running). `pages/mod.rs` `Login` starts the login only without a session; a failed login (e.g. the provider refusing the user's groups) shows an alert with a retry button, as starting the next login right away would redirect forever. Local users (password = name): `admin`, `planner`, `reader`.

### Plans
Plan 0 is the baseline (`BASELINE_PLAN_ID` in backend and frontend, `Plan.isBaseline` in GraphQL): its `port_usage` rows are the current state. Every other plan holds planned changes on top of it; implementing merges them into the baseline and deletes the plan, so there is no plan status (SQL uses the literal 0). The baseline can't be changed directly, renamed or implemented. `planned.rs` exposes `PlannedPanel` / `PlannedPort` (entity + plan context); `port_usage` rows are plan-scoped; what a port holds in a plan comes only from the SQL function `effective_port_usage(plan)` (migration `effective-port-usage`: the plan's rows and the baseline's it doesn't replace, without rows removing a fiber), from Rust through `PortUsage::effective`, the loader's `EffectiveUsage` (`PlannedPort.usage`, `currentUsage`, `PortUsage.otherSide`, one query per plan), `cable_usages_at` and `PortUsage::trace`, so the panel pages and the Netbox sync can't disagree; `PortUsage::trace` is the one way to follow a signal (`cableSideEndPort`, `panelSideEndPort`, the circuits of the Netbox sync, from a connector's back): one recursive query along the fiber to the next port and through a port to its other side, alternately, stopping at a port side reached already (`Trace::looped`); `Plan.changedPorts` (`planned.rs` `PortChange`) compares a plan's rows with the baseline in three queries: the ports it changes, each with its fibers now and in the plan (a row without fiber removes it, one equal to the baseline changes nothing). `mutation/implement.rs` applies a plan; `mutation/sync.rs` diffs a plan against NetBox devices/rear ports and reports `SyncIssue`s before syncing (only the circuits). Netbox shows the plan marked `plan.netbox_active` (`Plan.netboxActive`, `setNetboxActivePlan`; implementing it makes the baseline active), synced automatically (`docs/netbox-sync.md`): triggers insert a row into `netbox_sync_anstoss` in the transaction of every change affecting its circuits, the worker `netbox/auto_sync.rs` (started by `main.rs`, woken after every committed request) runs the sync when there are such rows or `sync_interval_h` passed since the last run, one transaction per run (holding a Postgres advisory lock, deleting the rows it read, so changes during it stay pending; a failed run is rolled back and its error stored afterwards), retries a failed run after 1, 2, 5, then 10 minutes, and stores the result: the issues (in `netbox_sync_issue` as JSON, with the ids of ports and panels and a `NetboxPortRef` snapshot of Netbox's rear ports; Netbox stays as it was) or the error; the query `netboxSync` tells where it stands, `syncNetbox` runs it right away.

### Database
Diesel 2 with `diesel-async` + deadpool; PostGIS geometries via `postgis_diesel`. Geometries are stored in LV95 (EPSG:2056, `schacht.geom`, `trasse.geom`; `local/data.sql` converts its WGS84 sample data on import). For the map GraphQL delivers them as WGS84 `GeoPoint { lat lng }` (`Schacht.location`, `Duct.line` from Schacht A to Z, `Cable.line`, missing if its ducts have a gap), converted by PostGIS with `st_transform(geom, WGS84)`; `Schacht.position` is the stored point in LV95 (`Lv95Point { e n }`, like `convertPoint`). Positions typed by users go through `graphql/geo.rs`: `PositionInput` (`@oneOf` LV95 or WGS84), converted by PostGIS as well (`to_lv95`, the query `convertPoint`) and refused outside of Switzerland. Geometries are master data like cables: a change applies to all plans at once. Every Schacht and duct has an owner (`eigentuemer`, GraphQL `owner: Owner!`, `listOwner`; an insert without one gets the owner marked `standard`, by trigger), and the columns for the Leitungskataster delivery (`lagebestimmung`, `trasse.leitungskataster`, `schacht_typ.lkmap_objektart`, `lk_lieferung`, see `docs/leitungskataster.md`); triggers keep `geaendert_am` of Schächte and ducts up to date (also when a Schacht moves, its type or owner changes), so don't set it by hand. Table definitions are in `backend/src/db/schema.rs`, entities in `backend/src/db/entity/`. Note `diesel.toml` points `print_schema` at `src/schema.rs`, but the live file is `src/db/schema.rs` — move/merge the output if you regenerate with `diesel migration run`.

### Frontend
New and changed pages follow `docs/frontend-konventionen.md`, checked only locally (no CI) by `local/konventionen/run.sh` and Clippy's `disallowed_*` lints of `cable-editor-frontend/clippy.toml` (a new route needs its entry in `pages.mjs`, an exception a `konventionen:ignore` comment with its reason): names of actions (Speichern, Anlegen, Abbrechen, Löschen, Entfernen), how objects are linked, where an error appears (alert or toast), the toast after every change and the warning about unsaved changes. Where the code still differs, bring it in line when you touch it and say so.

`pages/router.rs` defines `AppRoute` (yew-nested-router); plan-scoped views are nested under `AppRoute::Plan { plan_id, view }`. `AppRoute::content` builds PatternFly's page layout by hand (no `Page` component, no masthead/sidebar): `<main>` with a breadcrumb `PageSection` (menus in `components/menu/`) followed by the page. The breadcrumb is one hierarchy Planung › area › Schacht › panels › view, the areas grouped by purpose in the area menu (`MenuDropdown` `groups`: Planung, Objekte, Stammdaten, Lieferung; the UI calls a plan „Planung“, checked by the rule `plan-statt-planung`): each menu offers one level only, with the entry of the current page selected, so exactly one entry is active per menu: the menu of an object type (`ListCabinet`, `ListDuct`) lists only the objects (the Schächte), the next menu the views of the object above plus the objects one level down (a Schacht's views and root panels, a panel's views and child panels; on a panel's pages the panel is selected, otherwise the view; `ListPanel` builds one such menu per level). Menus use the own popper-free `PopupMenu` (`components/menu/popup.rs`, see its doc comment) and value choices `components/select.rs` `Select` (patternfly-yew's native `FormSelect`, denied by Clippy elsewhere: it sets the value only when the value changes, so `Select`'s options select themselves, else an option added after the value, e.g. loaded later, leaves the placeholder shown); patternfly-yew's popper-based `Dropdown`/`SimpleSelect` log console errors and are not used. Every routed page wraps its output in `components/page_layout.rs` `PageLayout` (h1 title section + content section; title `"<view> – <object>"` via `object_title`, just the view while loading), so headings inside a page start at `h2`; `.app-page` in `style.scss` lets the document scroll instead of the main container, so pages must not add their own outer padding. Pages live in `pages/`, reusable pieces in `components/`. PatternFly's dark theme (`pf-v6-theme-dark` on `<html>`) follows `prefers-color-scheme` through a script in `index.html`, off while printing; styles use PF tokens (`--pf-t--global--*`), fixed colours only for the fibre colours and the print styles. Wherever a page (other than an edit page) shows a Schacht, panel, cable or duct, it links to it with `components/links.rs` (`SchachtLink` → overview, `PanelLink` → connection overview, `CableLink` → cable page, `DuctLink` → duct page, `SchachtTypLink` → type page, `OwnerLink` → the list of owners, who have no page of their own; a plan `components/plan_link.rs` `PlanNameLink` → its Schächte). Buttons and links to a view of the plan are a `PlanLink`; a raw router `Link` is denied by Clippy (`disallowed-types`), only `plan_link.rs` builds one. Complex components (data fetching, state, event handling) are struct components (`impl Component`: `create` sends a fetch message, `spawn_local` + `util::get_credentials`, `changed` refetches on new ids); function components only for very simple ones. Hooks have struct counterparts, e.g. `label_printer::check_printer_supported` for `use_printer_supported`, `util::get_backdrop`, and `components/table.rs` `ListModel` instead of `use_table_data`. `PlanView::Cabinet { view: CabinetView::Overview }` (`pages/cabinet/overview.rs`) is the Schacht's single page, built for phones in the field: its panels (links to their connection overview, panel labels), the cables ending there (cable labels) and its properties, edited inline (no separate "Bearbeiten" page or button): `CabinetProperties` (`pages/cabinet/properties.rs`) renders only its form and map, not its own `PageLayout`, and is embedded here with `cabinet: IdOrNew::Id(id)`; readers see it read-only, planners edit and admins see "Löschen" there, same as before when it was its own page (`onsaved` lets the overview refetch the Schacht's name and "Geändert" after a save, since the component now stays mounted instead of navigating away). `CabinetProperties` edits name, type, owner (a new Schacht: the default one), position and Lagebestimmung (default `ungenau`, never proposed from the device's accuracy), and, wrapped in a `PageLayout` by the router instead, creates a new Schacht under `PlanView::NewCabinet { id }` (prop `IdOrNew`, the way to tell a new object from a stored one; a new object's `IdOrNew::Temporary` id lives in the path, e.g. `/plan/0/newcabinet/<uuid>` from the list's link, so it stays the same when the route renders again or the page reloads and several new objects can be told apart): the position is set by clicking the map or dragging the marker, typed in LV95 or WGS84 (both numbers can be pasted into the first field; swapped values and LV03 get a correction proposal, `geo/coordinates.rs`) or taken from the device's location; readers get it read-only (a `Select` can't be disabled, so they get a text field). The map also draws all other ducts and Schächte for context (`draw_base`, reusing `graphql/authenticated/map.rs`'s `MapData`/`fetch_map_data`, the same query `components/cable_map.rs` uses), leaving out the Schacht being placed itself, whose own marker (`.schacht-properties__marker`) stands out from the rest with the warning colour also used for a selected duct. Editing its panels stays a separate page, `CabinetView::Edit` (`pages/cabinet/edit.rs`, opened by a button on the overview for planners); the breadcrumb switches between the two (`CabinetView::ALL`). The duct's overview (`DuctView::Show`) still keeps its separate "Bearbeiten" page (`DuctView::Properties`) rather than embedding it, unlike the Schacht and the cable (`docs/frontend-konventionen.md`, "Entschieden"). On phones, tree tables only show cells with a column label, and `PopupMenu`s open as a sheet at the bottom. `PlanView::Map` (`pages/map.rs`) is the plan's map on swisstopo's national map (WMTS, EPSG:3857, tiles up to zoom 18, enlarged further in) or, chosen with the control on every map (`geo::map::add_background`, remembered in `localStorage`), the aerial image (sharp up to zoom 20); the cadastral map was dropped as its server draws lines per tile, which leaves them offset or cut at every tile border: the Schächte with a position (`Schacht.location`) as markers labelled with their name (their type's icon, an `<img>` like elsewhere, a circle without type; `geo::map::schacht_marker` on every map) (a click on a marker or its name opens the Schacht overview) and the ducts (`Duct.line`); a click on a duct (a wide invisible line takes it) highlights it and shows a card above the map with a link to its page and its Schächte and cables as links, a click on the map closes it. The map's container must stay the same element: Yew matches unkeyed siblings from the end, so the card's div is always rendered and only its content changes. The cable page (`pages/cable/edit.rs`) has a map beside its form (`components/cable_map.rs`): all ducts and Schächte, the path as being edited (unsaved) drawn over them; while editing, a click on a duct connecting to an end of the path adds it, on the first or last segment removes it (a single one at the front, which empties the path), and an empty path starts with any duct. A cable without segment can't be saved (the page disables it, `updateCable` and `createCable` refuse an empty path). A new cable is this page under `PlanView::NewCable { id }` (prop `IdOrNew` like a new Schacht, from the list's link; no dialog): it starts with one bundle of 12 fibers and no path, „Anlegen“ sends name, fibers and path at once (`createCable`) and opens the cable's page. Ducts are wired into the navigation like cables: the area "Trasse" with the list `PlanView::ListOfDucts` (`pages/duct/list.rs`), the object menu `ListDuct` in the breadcrumb and `PlanView::Duct` with the views `DuctView::Show` (`pages/duct/show.rs`: Schächte, length, cables, owner, what the Leitungskataster takes from it and a map of its line) and `DuctView::Properties` (`pages/duct/properties.rs`, also `PlanView::NewDuct { id }` like a new Schacht; "Bearbeiten" like the Schacht's, opened by the button of `DuctView::Show`, back to it after saving, but not after storing the course): Schächte (fixed once cables run through it), description, owner (a new duct: the default one), whether it is delivered to the Leitungskataster, Lagebestimmung (default `ungenau`) and width, and the course from a GeoJSON or GPX file (`geo/geo_file.rs`: lines of the file, its coordinate system from the GeoJSON `crs` member or guessed from the numbers, GPX is WGS84). `checkDuctLine` shows it as preview before `setDuctLine` stores it: the backend (`graphql/duct_line.rs`) converts it to LV95, turns a line running from Z to A and leaves out ends within 0.5 m of their Schacht (the stored `trasse.geom` holds only the points between the Schächte, the view adds them; none: a straight line); an end further than 10 m from its Schacht needs `confirmed`; a duct without description is named after its Schächte (`list_ducts::duct_title`). The area „Eigentümer“ is `PlanView::ListOfOwners` (`pages/owner/list.rs`): the owners with their Schächte and ducts, for admins a menu per row (edit in a dialog in the backdrop, set as default, delete) and a button for a new one. The area „Schachttyp“ is `PlanView::ListOfCabinetTypes` (`pages/cabinet_type/list.rs`) with `PlanView::CabinetType { id }` and `PlanView::NewCabinetType { id }` (`pages/cabinet_type/properties.rs`, `IdOrNew` like a new Schacht; object menu `ListCabinetType`): name, icon, Objektart and inner dimensions. The area „Leitungskataster“ (admins only) is `PlanView::Leitungskataster` (`pages/lkmap.rs`): the delivery for the whole network (`lkmapExport`) with where it stands (`lkmap::DeliveryState`: nothing to deliver, never delivered, changed since the last confirmed delivery with the week to deliver, not delivered in this quarter, up to date) and the download of its ZIPs (`util::save_file`), its report (what lacks a position) and its deliveries, to confirm or take back; below a map of the perimeter and the delivered ducts. The area „Netbox“ (admins only) is `PlanView::Netbox` (`pages/netbox.rs`): where the automatic sync stands, the plan Netbox shows, the error or the issues of the last run (`components/netbox.rs` `view_issues`) and „Jetzt synchronisieren“; while Netbox isn't in sync, `NetboxHint` in the breadcrumb bar (before `UserMenu`, asking again on every navigation and every minute) says so to everyone, for admins with the way to that page. The plan's page (`pages/planning/edit.rs`) shows whether Netbox shows the plan and lets admins activate it. „Arbeitsauftrag“ (`PlanView::WorkOrder`, `pages/work_order.rs`, in the area menu of every plan but the baseline) is what is to be done in the field to implement the plan, per Schacht and root panel, from `Plan.changedPorts`: the loops to cut, a line per pair of cables with only the fibers' colour labels, compact for phones (looped now, not in the plan; a loop only means a fiber stays uncut, a cut fiber can't be looped again, so a loop the plan adds is no work), the splices (splice ports, and the pigtail spliced to the cable on a connector's back) and, less important, the plugs on a connector's front, each with its fibers now and in the plan; a `Select` limits it to one Schacht, „Seite drucken“ prints every Schacht on a sheet of its own (`.work-order__*` in `style.scss`, its own phone layout instead of PatternFly's grid mode, which would apply to the narrow print page too). Icons are SVG files shown as `<img>` with a `data:` URL (`schacht_types::icon_src`), never inline, so a script in an uploaded SVG doesn't run; the backend accepts only well-formed XML with an `<svg>` root. The pages drive Leaflet through the `leaflet` crate directly, with the shared pieces in `geo/map.rs`: a component keeps its map in a `MapHolder` (renders its `container()`, `create()`s the map on the first render (on touch screens, `pointer: coarse`, one finger scrolls the page and two move the map, one finger moving across it shows a hint, `TouchGestures`), `replace_layers` for what depends on its state, removes the map when dropped) and draws with `schacht_marker`, `duct_line`, `duct_hit_line`, `hover_text`, `fit_points` and `div_icon` and a page with a map beside its content in `.map-layout` (`geo/` holds plain helpers, `components/` only Yew components that aren't pages). The crate's `bind_tooltip_with_content` calls a method Leaflet doesn't have, bind a `Tooltip` instead, and its `DivIcon::new` creates an `L.Icon` (use `geo::map::div_icon`); SVG colours come from CSS classes (`.map-view__schacht`), as Leaflet's colour options are attributes that can't take tokens. The app is installable (`assets/manifest.webmanifest`, `display: standalone`, icons in `assets/icons/`: `icon.svg` a Schacht with fibres running through it, `favicon.svg` a simpler one for small sizes, the PNGs rendered from them), without a service worker: it can't work offline and would have to be JavaScript. Auth uses `yew-oauth2` (OpenID); `graphql::query`/`mutate` attach the bearer token from `OAuth2Context` and return the data, a refused request as `FrontendError::User`, other GraphQL errors as `FrontendError::Graphql` (shown as a danger alert, each message with its `ErrorOrigin`), a response with neither data nor errors as `FrontendError::EmptyResponse`, an object a page asked for that doesn't exist as `FrontendError::NotFound { kind, id }` (`FrontendError::not_found`, worded like the backend's `UserError::NotFound`: "Trasse 7 nicht gefunden") and data not fitting the query as `FrontendError::InvalidResponse` (the data is read as JSON first, as a response with errors may lack fields). The GraphQL URL is derived from `window.location`, which is why `trunk serve` proxies to the backend.

The backend never words messages for users (see `docs/fehlermeldungen.md`): a check refusing a request returns a `UserError` variant carrying the data its message needs (names, counts, limits), which reaches the frontend in `extensions.userError`; all texts are in the frontend's `error/messages.rs` (an exhaustive `match`, the Netbox sync's `SyncIssue` texts as well). Resolvers return `graphql::error::ApiResult`: `?` on the error of a library (trait `Origin`, add new ones there) records the library and the line of the `?`; the GraphQL error carries it with an id in `extensions.origin` (`ErrorOrigin` in the common crate), logged with the same id. Problems that are the result of a check (several at once, referring to objects, like `SyncIssue`) are explicit types in the schema instead. The mock throws the same `userError`s, `check.mjs` checks refusals by code and data. Errors belong in the UI, never only in the console: return them as `FrontendError` and show them as an alert on the page (`IntoPropValue<Html>` for `&FrontendError`), or, where replacing the page would lose unsaved input (e.g. a failed request behind a button), as a danger toast via `util::toast_error` (every successful change to stored data ends with a `util::toast_success` in the past tense, "Schacht gespeichert", also in the editors and before the page changes afterwards; a dialog in the backdrop doesn't know the toaster, so it reports success and failure to the page that opened it, which toasts; "Speichern"/"Anlegen" are `disabled` without valid changes, checked by `local/konventionen`). A page with input not stored yet holds a `components/unsaved.rs` `Unsaved` and calls `set(has_changes)` after every render (`false` while loading or read-only, a new object only once `touched`); `UnsavedGuard` around the router, which can't hold back a navigation, catches clicks on links (capture phase on the document) and `popstate` (capture phase on the window, before the router; the address moves back to the page) and asks "Änderungen verwerfen?" (Verwerfen / Weiter bearbeiten), `beforeunload` gives the browser's warning; what a page opens itself (`util::navigate` after saving) isn't asked, `local/konventionen` checks it (`LEAVE_FLOWS`). The installed app has no reload or back button (iOS), so every error must leave a way on (`components/recovery.rs`): `AppRoute::content` wraps breadcrumb and page in a `RetryScope`, whose `Recovery::Retry` context lets the alert of a failed connection or an unexpected server error offer "Erneut laden" (builds breadcrumb and page anew, so they load their data again; unexpected server errors also "App neu laden", e.g. after a new version changed the schema); errors before the router (`App`, `UserProvider`) provide `Recovery::Reload`; dialogs provide nothing, as reloading would lose their input. A breadcrumb menu that couldn't be loaded shows `menu::MenuError` instead of an alert, which doesn't fit into the breadcrumb: "Nicht geladen", opening to the error with its details (`FrontendError::title`, `details`) and "Erneut laden". Messages keep their technical cause for those who can tell what it means. Other shared pieces of components: a port is shown by `graphql::authenticated::port_label` ("Port <n>" without label) after the path of its panel (`write_panel_path`, `write_port_label`: "Schacht: Parent > Panel : Port"), a fiber by `components/fiber.rs` `FiberNumber` ("<bundle>-<fiber>" in its colour), a point in time by `local_time`; `util::navigate(scope, plan_id, view)` opens a view of the plan, `components/dialog.rs` `confirm_delete(scope, kind, name, on_confirm)` is the click handler of a delete button (asks in the backdrop first: title "<kind> löschen?", buttons Löschen / Abbrechen), `ask_delete` asks the same from elsewhere (e.g. a menu item). A button showing only a symbol is an `components/icon_button.rs` `IconButton` (`aria-label` and `title` from `name`; patternfly-yew's `Button` has no `title`, `PopupMenu` sets it from its `aria_label`), printing the page (`window.print()`) only happens in `components/print_page.rs` `PrintPageButton` („Seite drucken“), labels on the label printer are „Etikett drucken“. Console logging (`log::warn!`) is only for conditions that aren't errors, e.g. the label font falling back. No panics in reachable code (a panic takes down the whole wasm app): Clippy denies `unwrap_used`, `expect_used` and `panic` in the frontend (`[lints.clippy]` in its `Cargo.toml`); state the browser decides (document, canvas context, location) becomes a `FrontendError` (`Browser`, `BrowserMissing`), `expect` only for programming errors such as a missing Yew context, with `#[allow(clippy::expect_used)]` and its reason. That still leaves panics from a dependency (indexing, an `unwrap` Clippy can't see), so `main.rs` installs `console_error_panic_hook` before rendering, the only thing standing between such a panic and a silently blank page with nothing in the console; below even that, `index.html` has a plain-JS `error`/`unhandledrejection` listener (no dependency on the wasm app having started at all) that logs the full error and shows a minimal "Die Anwendung konnte nicht gestartet werden" message instead of leaving the page blank. A failed action whose input is still on the page (saving, deleting, the panel editors, the plan's actions) is a `util::toast_error` (its body is the `FrontendError`'s German `title()`), a failed load an alert.

### Label printing (Brady M211)
- Printer: Brady M211 over Web Bluetooth (Chrome/Edge only), tape M21-1250-427 (self-laminating, 1.25" wide, continuous). Label text is `"<cable> - <far schacht>"` (`graphql/authenticated/schacht_cables.rs`; `Schacht.cables` paths are oriented from that Schacht, so `farSchacht` is the destination).
- Wiring: `@bradycorporation/brady-web-sdk` in `node/package.json`; `index.html` maps it with an importmap (must precede any module script) and copies its whole `dist/` to `/brady-web-sdk/` (the bundle loads its wasm/pdf.js relative to itself). `BradyProvider` wraps the `BackdropViewer` in `pages/mod.rs` so the connection survives navigation and dialogs (rendered by the viewer) can `use_brady()`; `PrinterStatusBar` next to the router shows the connection (icon button to connect/disconnect, printer, tape, battery) fixed at the bottom of every page, only in browsers with Web Bluetooth.
- `components/label_printer.rs`: `PrintLabelButton` connects, waits for the reported tape and opens a dialog with a live preview (the geometry follows the printer status, e.g. a cartridge change while it is open), a choice between its `texts` and, with `diameter`, the cable diameter (last value in `localStorage`). Cable labels come from the Schacht overview, panel labels (`PanelLabelButton`: name or path from the root panel joined with " - ", no diameter) from the Schacht overview and the panel overview (`components/panel/show.rs`); label rendering on a canvas in Barlow Bold (DIN-like, npm `@fontsource/barlow`, copied by `index.html`, declared in `style.scss`; its straight shapes show fewer steps at 203 dpi than Roboto), loaded before the dialog opens. Text height is capped at 70% of the diameter; small text is repeated across the band (as many copies as fit, with half a text height between them, within the 80% a maximal line takes: 3 mm → 3, 4 mm → 2, from ~5 mm → 1) so it reads from more sides of the cable (`text_layout`). The label is cropped to the glyphs along the tape.
- `LabelGeometry::from_status` derives the layout from the tape the printer reports (`PrinterStatus::print_zone`, `supply_width`, model), mirroring the SDK: text band = print zone width, else the tape width covered by the head (M211 0.63", M511 1.44"). Die-cut labels are refused. Verified offline for M21-1250-427 and M21-750-499.
- SDK quirks handled there, verify on hardware before changing:
  - Printing before the printer reported its supply fails (`Invalid typed array length: -1`), so it waits for `supply_width`.
  - The SDK scales the image height to the text band (0.43" zone on M21-1250-427); label length follows the image aspect ratio. The M211 adds ~0.87" blank feed per label (hard-coded in the SDK).
  - For tapes with a print zone the SDK places the zone without subtracting the tape the head does not cover (0.62" on the 1.25" tape), which yields an empty job and a print timeout; the geometry shifts it back via the x print offset.
  - `supplyYNumber` is numeric (e.g. `4900577`), not the part name.
- Updating the crate: push it, then change only its rev in `Cargo.lock` (`cargo update -p brady-web-sdk` also churns unrelated `windows-sys` entries). To test local crate changes before pushing: `--config 'patch."https://git.panter.ch/open-source/brady-web-sdk-rs.git".brady-web-sdk.path="../brady-web-sdk"'` (revert `Cargo.lock` afterwards).
